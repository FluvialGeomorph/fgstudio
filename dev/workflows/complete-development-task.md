# Complete a development task

## Trigger

A requested repository change is ready to implement.

## Procedure

1. Read the workflow named by the applicable `AGENTS.md` route before choosing the implementation or tools.
2. Confirm the requested scope and current Git evidence.
3. Define the usable outcome and its acceptance evidence, then implement the cohesive change needed to deliver it while preserving unrelated work. Minimize unnecessary code and scope, not the functionality delivered per turn.
4. Run checks proportionate to risk.
5. Edit the existing artifact that owns the changed requirement or procedure; remove conflicting guidance rather than appending a completion narrative. For changed data inputs/outputs, ownership or persistence, apply the function/data completion check in `developer-documentation.md` and update the affected mappings in the same task.
6. Review the final status and diff. Verify that the task route reaches current instructions without a historical report, and remove duplicate or superseded machinery.
7. Create a checkpoint only if useful unfinished state remains.

## Completion evidence

Report changed behavior, verification performed, remaining risks, and any durable artifacts updated.

## Delivery cadence

The unit of delivery is an authorized user outcome, not one function, test,
diagnostic experiment or documentation edit. For a feature, state what the analyst
will be able to do and where it fits in the whole app. Include the necessary
backend, UI, persistence, error handling, verification and maintained documentation
in the same working turn where practical. A requested investigation or docs-only
task has its own outcome; do not manufacture app changes to satisfy this rule.

Continue through routine intermediate steps without requesting another
"proceed." A passing technical probe is evidence for the next implementation
step, not an automatic stopping point. Backend-only work needed by the authorized
feature does not require a separate approval. Ask when an unresolved scientific
choice, missing required information or materially expanded scope needs the owner;
continue independent authorized work while that question is pending. Preserve
scientific authority, explicit analyst datum-operation selection and provenance.

Run focused checks as the implementation develops. Broaden them when changed
boundaries or unresolved risks warrant it; repeat successful checks only after
relevant changes or new evidence. Consolidate documentation updates and published
site builds after the behavior settles. Refresh the whole-app preview for the
reviewable result, not for each internal milestone. Dev-only prose changes need
diff and link review, not R tests, package builds, site builds or app restarts.

Before handing back control, compare the result with the stated outcome. If it
is incomplete, continue unless there is a concrete blocker or execution limit;
report that limit and the remaining work honestly. Do not substitute a small
cosmetic change for the requested feature. If a checkpoint is needed, record the
outcome, completed evidence, exact blocker and next integrated action. Distinguish
deferred work from the selected next task so a later session does not resume a
sequence of increasingly narrow probes by default.
